# ADR-0004: Cloudflare R2 with per-tenant prefixes

- **Status:** Accepted; amended by [ADR-0020](0020-single-store-application-without-multi-tenancy.md) — one store per installation, so tenant, brand and landlord passages below are history
- **Date:** 2026-09-26
- **Spec reference:** §2 (FINAL: S3-compatible, R2 default), §6.9, §4.4

## Context

Media must never live on the application server's disk (FINAL). Storage must be tenant-aware,
CDN-served, and support both public product images and private files (invoices, exports,
payment receipts) behind signed expiring URLs. The platform is Cloudflare-fronted already.

## Decision

**Cloudflare R2, one bucket per environment, with a per-tenant key prefix.**

```text
r2://platform-prod/
  tenants/{tenant_id}/media/{media_id}/{conversion}/{random_filename}.webp   public
  tenants/{tenant_id}/private/invoices/{order_ulid}/{random}.pdf             private
  tenants/{tenant_id}/private/exports/{job_ulid}/{random}.csv                private
  tenants/{tenant_id}/private/receipts/{payment_ulid}/{random}.jpg           private
```

- Two Laravel disks per tenant, both configured by the filesystem bootstrapper with the
  tenant's prefix: `tenant_media` (public, CDN-served) and `tenant_private` (no public access,
  signed URLs with a short TTL).
- Public media is served through a Cloudflare custom domain on the bucket
  (`cdn.<brand-domain>` or a shared platform CDN host), so images are edge-cached and never
  touch the origin.
- Filenames are **randomised**; the original filename is kept only as metadata. Object keys
  are therefore unguessable even for public media.
- spatie/laravel-medialibrary generates conversions (WebP/AVIF, multiple sizes) in **queued
  jobs** on the `media` queue, with tenant context.
- Upload security (spec §6.9): MIME validated by content not extension, size limits,
  **images re-encoded** on upload (which strips EXIF and any embedded payload), **no SVG from
  untrusted uploads**, and private files never publicly readable.
- Bucket-level: versioning on, a lifecycle rule expiring incomplete multipart uploads, and
  public access allowed only through the CDN domain for the media prefix.

### One bucket, not one bucket per tenant

Per-tenant prefixes are the default rather than per-tenant buckets, because bucket count is a
provisioning and quota liability at 50+ tenants, and R2 has no per-bucket feature the platform
needs. A tenant that contractually requires its own bucket (or its own R2 account) is
supported by the same code: the disk configuration is resolved per tenant, so pointing one
tenant at a different bucket or credentials is configuration, not code. That mirrors the
dedicated-topology principle in spec §4.3.

## Consequences

### Positive

- **No egress fees** on R2, which matters for an image-heavy catalog served to a mobile-first
  Pakistani audience, and it removes the main cost objection to serving every image from
  object storage.
- Cloudflare is already in the stack for CDN and WAF, so there is one fewer vendor, one
  billing relationship, and one place to configure cache rules.
- S3-compatible API means the Laravel S3 driver, MinIO for local development, and any future
  migration to another S3 provider all work unchanged.
- Tenant export is a prefix copy; tenant deletion is a prefix delete. Both are simple,
  scriptable operations with no cross-tenant risk.

### Negative / costs

- Prefix-based isolation is enforced by the application (the bootstrapper), not by separate
  credentials, so a bug that bypasses the disk abstraction could in principle read another
  tenant's key. Mitigated by isolation test #6, by never accepting a caller-supplied path, and
  by randomised keys.
- R2 has no built-in image transformation; sizes are generated by the app at upload time via
  medialibrary conversions. Cloudflare Images can be added later if on-the-fly transformation
  becomes worthwhile.
- Point-in-time restore of media relies on bucket versioning rather than snapshots, so the
  restore drill must cover "restore a tenant's media to yesterday" explicitly.

### Risks and mitigations

| Risk | Mitigation |
|---|---|
| Path traversal into another tenant's prefix | The disk is always resolved from tenant context; user input never contributes to an object key; keys are generated, not accepted |
| A private file gets a public URL | Private files live on a separate disk with no public base URL; a test asserts that a private key returns 403 without a signature |
| Malicious upload (polyglot image, SVG with script) | Content-based MIME check, re-encode on upload, SVG rejected from untrusted sources, CSP on the storefront |
| Vendor outage | Images are edge-cached; the S3-compatible abstraction means a second provider can be introduced without code change |

## Alternatives considered

| Alternative | Why not |
|---|---|
| AWS S3 + CloudFront | Egress cost on an image-heavy catalog, and a second CDN alongside Cloudflare. Still supported by the same driver if a client demands AWS. |
| Bucket per tenant | 50+ buckets to provision, monitor and quota, with no feature gained. Available as a per-tenant override where a contract requires it. |
| Local disk plus rsync to a CDN origin | Forbidden by the spec, and it makes horizontal scaling and tenant export needlessly painful. |
| Storing media rows in PostgreSQL (bytea / large objects) | Bloats per-tenant backups, defeats CDN caching, and turns image delivery into database load. |
