# ADR-0008: ULID public identifiers, integer minor-unit money

- **Status:** Accepted; amended by [ADR-0020](0020-single-store-application-without-multi-tenancy.md) — one store per installation, so tenant, brand and landlord passages below are history
- **Date:** 2026-09-26
- **Spec reference:** §6.1 (FINAL: ULIDs public, internal ids never exposed), §6.3 (FINAL: money as integer minor units)

## Context

Both rules are FINAL in the spec. This ADR records *how* they are implemented, because both
are the kind of decision that is nearly free on day one and extremely expensive to retrofit
after a mobile app is consuming the API and a year of orders exists.

## Decision

### Identifiers: `BIGSERIAL` internally, ULID publicly

Every entity reachable by API or URL carries both:

```php
$table->id();                              // BIGSERIAL, internal joins and FKs
$table->char('ulid', 26)->unique();        // the only identifier ever exposed
```

- **Joins, foreign keys and indexes use the integer id.** It keeps indexes narrow and joins
  fast, which matters most on `order_items`, `inventory_movements` and `product_variants`.
- **URLs, API payloads, OpenAPI schemas, webhook payloads and CSV exports use the ULID only.**
  An architecture test asserts no API resource exposes a field named `id` bound to the integer
  column, and route binding is configured to resolve models by `ulid`.
- ULIDs are chosen over UUIDv4 because they are **lexicographically sortable by creation time**
  — useful for cursor pagination and for debugging log correlation — and are shorter in URLs
  (26 chars, Crockford base32, no hyphens, case-insensitive).
- The **tenant id is itself a ULID** and is reused as the suffix for the database name, cache
  prefix, storage path and Typesense collection, so every namespace is derivable from one
  value (see [ADR-0001](0001-multi-database-tenancy-with-stancl-tenancy.md)).

Why not ULID as the primary key: a 26-byte character PK widens every index and every foreign
key in the database, and on the tables that grow fastest (movements, order items, transactions)
that cost compounds. The dual-key approach keeps the public contract opaque without paying that
price.

### Money: `BIGINT` minor units plus an explicit currency

```php
$table->bigInteger('total_amount');        // paisa — 249900 means Rs 2,499.00
$table->char('total_currency', 3);         // 'PKR'
```

- Column pairs are always named `<thing>_amount` / `<thing>_currency`. A bare `price` column is
  a review rejection.
- A `Money` value object in the `Support` kernel wraps amount and currency, implements
  arithmetic, and **refuses to add two different currencies**. Models cast money columns to it.
- **No float ever touches money**, in PHP or in JSON. Percentages are stored as integer basis
  points (`rate_bps`, so 17% is `1700`), which keeps tax and discount maths in integers.
- Rounding is explicit and happens once per pricing stage, with the rule documented in the
  pricing pipeline; the stage order is fixed (line prices → promotions → coupons → shipping →
  tax → totals) so results are reproducible.
- The API always returns money as an object, including a server-formatted string, so no client
  ever formats or converts currency (see
  [api-conventions.md](../architecture/api-conventions.md) §2).
- An architecture test forbids `float` type declarations and casts in any class handling money.

`BIGINT` is used rather than `INTEGER` because PKR amounts in paisa exhaust a 32-bit signed
integer at about Rs 21.4 million — well within a plausible annual-revenue aggregate in a
reporting table.

## Consequences

### Positive

- Enumeration attacks and information leakage through sequential ids are structurally
  impossible in the public API. `/products/48` cannot be walked; a ULID cannot be guessed.
- Ids generated by the application, not the database, so a full object graph can be built in
  memory before a single insert — useful in importers and in tests.
- Money arithmetic is exact. No accumulated floating-point drift in order totals, tax lines,
  refunds, or the inventory valuation that depends on weighted-average cost.
- The currency travels with the amount, so a future multi-currency tenant needs no schema
  migration on the money columns.

### Negative / costs

- Two identifier columns per table, and developers must remember which one crosses the
  boundary. Mitigated by route binding on `ulid`, a base model trait, and the architecture
  test.
- Every money read and write goes through a value object, so ad-hoc `SUM(total_amount)` in a
  report returns a bare integer that the reporting layer must wrap. Accepted; reporting
  aggregates are typed at their edges.
- Formatting is a server responsibility, which means a small amount of duplicated locale logic
  between the admin and the API. Preferable to letting clients diverge on rounding.

### Risks and mitigations

| Risk | Mitigation |
|---|---|
| An internal id leaks into a payload or URL | Architecture test on API resources; route binding by `ulid`; code review checklist |
| A new money column is added without a currency | A test scans migrations for `_amount` columns lacking a matching `_currency` (or a documented single-currency parent) |
| Someone divides money and loses a paisa | `Money` exposes explicit allocation/rounding methods; unit tests cover discount splitting across lines |
| ULID collision | 80 bits of randomness per millisecond; a unique index makes a collision a caught error rather than silent corruption |

## Alternatives considered

| Alternative | Why not |
|---|---|
| UUIDv4 public ids | Not time-sortable (so cursor pagination and log correlation get harder), longer in URLs, and random-order insertion is worse if ever used as a key. |
| ULID as the primary key | Wider indexes and foreign keys on the fastest-growing tables, for no gain over the dual-key approach. |
| Hashids / obfuscated integer ids | Reversible obfuscation, not opacity — the sequence is still there once the salt leaks. |
| `NUMERIC(12,2)` for money | Exact in the database, but it arrives in PHP as a string that gets cast to float somewhere, which is exactly the failure mode the spec forbids. |
| Floats for money | Never. |
